2. LOGIC UNDERSTANDING
======================================================================
This spec implements a two-directional, per-vendor reconciliation between InForm SCI eCRF specimen records and two separate external vendor transfer files (BA Vendor on Tab 1, Central Vendor on Tab 2). After filtering InForm records to exclude deleted, 'not collected/not sent', DOV-uninitialized, or erroneous-visit records, it matches on the combination of Screening Number + Specimen ID (case-insensitive, with zero-padded IDs) in both directions: InForm records without a vendor match flag 'Missing in Vendor', and vendor records without an InForm match flag 'Missing in Inform', with the latter scenario sourcing Site/Screening/Subject Number fields from the vendor data per Note6.

1. This report reconciles specimen collection records entered in InForm (via the SCI eCRF form) against two separate external vendor transfer files: a BA Vendor file (output on Tab 1) and a Central Lab Vendor file (output on Tab 2). Each tab runs the same two-directional check independently against its respective vendor file. (inferred)
2. Before any matching occurs, filter the InForm SCI records to only those eligible for the logic: exclude deleted SCI records (Note2), exclude records where 'Reason Specimen Not Collected and/or Not Sent' is not blank (Note1), and exclude records where DOV is not initialized or the visit is marked erroneous (Note4).
3. For matching purposes, standardize identifiers: SITEID must be zero-padded to 4 digits, SCRNID zero-padded to 9 digits, and SUBJID zero-padded to 6 digits (Note5), so that comparisons between InForm and vendor values align correctly even if one side has fewer leading digits.
4. Specimen ID comparisons between InForm and vendor data are case-insensitive (Note3), so differing letter case alone should not cause a mismatch.
5. Scenario 1A: For each eligible InForm SCI record, form the combination of Screening Number + Specimen ID and check whether that combination exists anywhere in the vendor data (BA vendor for Tab 1, Central vendor for Tab 2). If no matching combination is found in the vendor data, output that InForm record's row with Error Message = 'Missing in Vendor'.
6. Scenario 1A Output=No condition: if the InForm record's Screening Number + Specimen ID combination IS found in the vendor data, it is not output - no discrepancy exists.
7. Scenario 1B: For each record loaded from the vendor data (BA or Central, respectively), form the combination of Screening Number + Specimen ID and check whether that combination exists among eligible InForm SCI records. If no matching combination is found in InForm, output that vendor record's row with Error Message = 'Missing in Inform'.
8. Scenario 1B Output=No condition: if the vendor record's Screening Number + Specimen ID combination IS found in InForm data, it is not output - no discrepancy exists.
9. When outputting a 'Missing in InForm' row (Scenario 1B), since there is no corresponding InForm record to source Site/Screening Number/Subject Number from, these fields are populated from the vendor data instead: Site and Screening Number come directly from vendor, and Subject Number is constructed as vendor's Siteid + '--' + vendor's Subjid (Note6).
10. When outputting a 'Missing in Vendor' row (Scenario 1A), by contrast, the identifying fields (Country, Site, Screening Number, Subject Number) are presumably populated from the InForm SCI record itself, since that's the record that exists and is missing its vendor counterpart. (inferred)
11. Each output row also includes the full set of available data fields from whichever side has data (InForm columns like Visit Name, Analyte, Schedule Time, Spec ID, Collection Date/Time always populated since it's the source of comparison; and the corresponding BA/Central columns populated only when a partial match or the vendor side has data), though the spec's Note6 implies the missing side's fields would simply be blank when no matching record exists on that side.
