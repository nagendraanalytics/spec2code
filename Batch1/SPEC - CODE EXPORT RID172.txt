2. LOGIC UNDERSTANDING
======================================================================
This report scans Aspera-loaded external data records from the Central Vendor File and/or BA Vendor File (governed by the Vendor parameter) and flags any record where one or more of a defined set of fields (NOMDAY, NOMHOUR, NOMTIME, DDT, DTM [conditional], REFID, ANALYTE, SAMPLE) is NULL, displaying only records with 'Output Yes'. When Vendor=ALL, matched records (by REFID and SCRNID) with multiple nulls across both files are combined into one row with a cumulative error message, but records with matching SCRNID but non-matching REFID are output as separate rows; when a single vendor is selected, only that vendor's columns appear and no cumulative messaging occurs. The DTM check is toggled on/off via the DTM parameter (default Y), and sorting for Vendor=ALL combines sort keys from both files.

1. The report operates on two distinct external vendor data sources: the 'Central Vendor File' (fields SITEID, SCRNID, SUBJID, NOMDAY, NOMHOUR, NOMTIME, DDT, DTM, REFID, ANALYTE, SAMPLE) and the 'BA Vendor File' (same fields, separate dataset), per the Column Heading and Form.Item Names lists.
2. The base parameter 'Vendor = ALL' means by default both Central Vendor File and BA Vendor File are included in the checks; this can be overridden by the Vendor parameter selection to restrict to only BA or only Central data (Comment 1).
3. For each field checked (NOMDAY, NOMHOUR, ANALYTE, NOMTIME, REFID, SAMPLE, DDT, and conditionally DTM), the spec defines a paired A/B logic: the 'A' version checks the field for NULL in the Central Vendor File, and the 'B' version checks the same field for NULL in the BA Vendor File.
4. Logic 1A: If NOMDAY = NULL in Central Vendor File, output 'Yes' (record flagged, message 'Missing NOMDAY in CV'); if NOMDAY <> NULL, output 'No' (not flagged). Logic 1B does the same check for NOMDAY in the BA Vendor File, message 'Missing NOMDAY in BA'.
5. Logic 2A/2B repeat this same NULL-check pattern for NOMHOUR in Central and BA files respectively, producing 'Missing NOMHOUR in CV' or 'Missing NOMHOUR in BA'.
6. Logic 3A/3B repeat the NULL-check pattern for ANALYTE in Central and BA files, producing 'Missing Analyte in CV' or 'Missing Analyte in BA'.
7. Logic 4A/4B repeat the NULL-check pattern for NOMTIME in Central and BA files, producing 'Missing Scheduled Time in CV' or 'Missing Scheduled Time in BA'.
8. Logic 5A/5B repeat the NULL-check pattern for REFID in Central and BA files, producing 'Missing Specimen ID in CV' or 'Missing Specimen ID in BA'.
9. Logic 6A/6B repeat the NULL-check pattern for SAMPLE in Central and BA files, producing 'Missing Specimen Type in CV' or 'Missing Specimen Type in BA'.
10. Logic 7A/7B repeat the NULL-check pattern for DDT ('DDT = Null in Central File' / 'DDT = Null in BA File'), producing 'Missing DDT in CV' or 'Missing DDT in BA'.
11. Logic 8A/8B check DTM, but are gated by the DTM parameter: the spec states 'DTM = Y' as a precondition before checking 'DTM = Null in Central File' (8A) or 'DTM = Null in BA File' (8B); this means the DTM null-check only runs when the DTM parameter is set to Y (default), producing 'Missing DTM in CV' or 'Missing DTM in BA'. If the DTM parameter is N (not applicable for the study per Comment 2), this check is skipped entirely.
12. When the Vendor parameter is ALL, and a Central record and BA record are matched (their REFID and SCRNID both match per Comment 3), if more than one of the checked fields is NULL across the two matched records, the report combines all the missing-field flags into a single cumulative error message on one output row, e.g. 'Missing NOMDAY in BA and NOMHOUR in CV', rather than listing them as separate rows.
13. Per Comment 4, if SCRNID matches between the Central and BA records but REFID does not match, the records are NOT treated as the same matched pair for cumulative messaging purposes -- instead their null-field results should appear in separate output rows.
14. Per Comment 5, when the Vendor parameter is set to a single vendor (BA or Central) rather than ALL, only the columns corresponding to that vendor are displayed in the output; the other vendor's columns are hidden entirely from the report.
15. Per Comment 6, when a single vendor is selected (not ALL), there is no cross-file matching or cumulative message logic needed -- each null field found in that vendor's file simply produces its own individual error message/row (as illustrated in the second Report Scenario example: Vendor=BA, DTM=N).
16. In the second Report Scenario (Vendor = BA Vendor, DTM = N), only BA-file checks are performed (Logic 1A-8A relabeled in that scenario as checks against 'BA Vendor File' only) and the DTM check is entirely absent from the list, confirming that DTM=N excludes the DTM missing-value check from the output. 17. Per Comment 7, when Vendor=ALL, the sort order for the final output must incorporate sorting variables from both the Central and BA files jointly (as opposed to sorting only by one file's keys), using the Sorting field list: SITEID, SCRNID, SUBJID, NOMDAY, NOMHOUR, NOMTIME, ANALYTE, SAMPLE.
18. Only records/rows where at least one checked field evaluates to 'Output Yes' (i.e., is NULL) are included in the final report; records where all checked fields are non-NULL ('Output No' for every check) are excluded from the display, since this is a report of records with missing required-field values.
